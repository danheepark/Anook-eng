# 문제 As-is: 운영 비효율/커뮤니케이션 비용

우리가 이 프로젝트를 왜 했는지? 어떤 문제를 발견했었는지?

호텔에서 반복되는 질문, 요청을 자언어로 프론트데스트 사람이 해결하는데 그리고 그걸 다른 부서로 전달하는데 어떤 어려움이 있었고 (호텔에서 인터뷰한 내용: 실제 호텔에서는 카카오톡으로 대체하여 사용 근무중) + 인수인계

실제 호텔 운영 관점에서 얼마나 많은 시간과 오류 (손님 응대와 각 객실 요청을 한번에 프론트에서 수행하면서 생기는 요청 누락 등)가 있었는지 

예) 호텔 운영에서는 고객 요청이 여러 부서로 분산되고, 외국인 고객 대응 과정에서 커뮤니케이션 비용과 업무 누락이 자주 발생합니다. 특히 자연어 기반 요청은 직원이 직접 분류하고 전달해야 하기 때문에 운영 피로도가 높았습니다.

→ 시장 조사와 프로트 데스크 반복 업무의 비율, 시간, 그로 인해 낭비되는 비용 조사 

# 솔루션 To-Be

이 서비가 호텔 workflow에 어떤 영향을 미치는지

실제 이 서비스가 바꿀 호텔 업무 flow 예시 보여주기 → 동시에 제품 소개 (기본 기능들)을 이해하기 쉬운 하나의 플로우를 만들어 보여줘야함 (한개의 스토리 만들기) 

고객:
“수건 2개 더 주세요”

↓

AI:
Housekeeping 분류

↓

업무 생성

↓

직원 처리

↓

완료 상태 반영

↓

고객 응답

이 기본 흐름!!!

예: “아늑은 고객의 자연어 요청을 AI가 분석해 적절한 부서로 자동 라우팅하고, 운영 가능한 구조화된 업무 형태로 변환하는 시스템입니다.”

→ 이렇게 하면 얼마나 짧게 한개의 업무가 처리될 수 있는지 계산하고 앞서 프론트 업무 시간 계산해서 몇%의 시간 단축이 있는지 숫자로 보여주기 

# Edge case (우리의 차별점)

우리가 가장 시간을 많이 쓴 곳은 ‘AI의 한계를 어떻게 처리했나’ 임 

AI가 완벽하지 않다는 것을 알고 그걸 기술적으로 보완한 예시들을 잘 보여줘야함 

1. AI 확신도가 낮거나 AI가 처리하기 어려운 요청은 Front Desk 로 이관 → 프론트 데스크 사람은 어떻게 채팅창에서 응대하는지 
2. AI Reasoning 추가 → 사람은 AI 를 100% 믿지 않는다. AI 가 완벽하게 자신들이 하던 일을 해낼거라고 믿지 않기 때문에 AI 가 왜 이렇게 판단했는지, 호텔 운영 관점에서 중요한 데이터임 

# Human-in-the-loop

AI가 모든 상황을 완벽하게 해결할 수 없다고 판단했고, 실제 운영 환경에서는 사람과 AI가 협업하는 구조가 중요하다고 생각해서 만든 Rag 자동화 → 데이터 계속 쌓이는 구조 만든거

우리의 최종 목적은 사람은 사람을 응대하는 사람이 할 수 있는 것에 집중하여 호텔 전체 서비스 질을 올리는 것

# 기술 설명

그냥 ‘이런 기술을 사용했어요’ 하고 나열하는게 아니라 왜 이 기술을 사용해야 했었는지 왜 이렇게 코드를 짜야했는지 (예: 호텔 운영에서는 같은 요청이라도 표현 방식이 매우 다양하기 때문에, 단순 키워드 기반 분류보다 문맥 기반 의도 파악 구조가 필요했습니다. 등
심지어 ‘왜 LLM을 사용했는지도 고객의 자언어 요청을 이해하는 기술이라서’ 라는 식으로 설명해야 함, 헥사고날 아키텍쳐도 왜 그걸 사용했는지 이유를 설명해야함) 

즉 ‘왜 이 구조가 필요했는지’ 

- 호텔 요청은 비정형 자연어다
- 부서별 업무 흐름이 다르다
- 예외 상황이 많다
- AI가 항상 정확하지 않다

# 확장 계획

## Design:

우리는 호텔에게 서비스를 제공하기 때문에 브랜드 색이 강하면 안됨 → 이 서비스를 이용하는 각 호텔마다 이미 브랜드 이미지가 있기 때문에 채팅창 디자인을 수정하거나 메인 컬러를 수정하거나, 또는 대시보드 디자인을 수정할 수 있는 옵션 주면 좋을 듯 

## AI:

퓨샷 추가 → AI 가 점점 더 정확도가 높아질 수 있도록 

그리고 추후에 실제 이 제품이 사용되면서 점점 호텔이 실제로 운영될 때 어떤 상황들이 있는지 AI에 데이터가 쌓이면 점점 더 정확도 높은 라우팅이 가능할 것이다
